# zcrowd: privacy claims and the check behind each one

The rule of this repository: no privacy claim without a check that can fail. Each claim below has a number, the check
behind it, and the result of that check on the final code; the list after the tables says what each check does not
cover. P claims are about what you type and what the commands do, T claims about `sync` over Tor, V claims about what the
verdict rests on, N lists the note about the network cut, and R is about release archives.

```
bash tests/audit.sh          # P1 to P11 and T1, T2, T5, T7. No network needed. Prints AUDIT OK only if every step holds
LIVE=1 bash tests/audit.sh   # also T3, T4, T6: a real sync over Tor under a leak check (needs the network and a C compiler)
bash tests/e2e.sh            # formatting, lints, all 140 tests, the command line on the fixtures, then the audit
```

A step that cannot run on a machine prints `SKIP ... (NOT VERIFIED)`; the audit counts the skips and its last line says
so. Every result on this page is of the final code (commit `dd7f9ee`; the commits after it change documents, the
screenshot, 3 lines of `.github/workflows/ci.yml`, 2 lines of `tests/e2e.sh`, 1 line of `web/test/headless.mjs` and the web page (its first box, then a grammar fix of it, README section 13); a result from a named CI run is of `70d5187`), run
on 2026-10-25 on a Linux desktop (x86_64) with Rust 1.97.1. The limits of the whole tool are the one list in
[README section 11](../README.md#11-honest-limits), and what was never run or seen is the one list
[NOT VERIFIED](../README.md#not-verified) at the end of the README.

## What leaves your machine

| Command | Network | What the other side learns |
|---|---|---|
| `sync` | The first default lightwalletd server that answers as mainnet (`https://zec.rocks:443`, `https://na.zec.rocks:443`, `https://eu.zec.rocks:443`, or each `--server` you name), over TLS, through Tor (the Rust Tor client arti, inside the process). Directly only with `--no-tor`. Tor itself downloads its relay directory from Tor relays and connects to them. | The server: the time, that someone runs zcrowd, the block range, the ids of the public transactions it fetches (the same for every user of that range). Your IP address only with `--no-tor`. Nothing about your wallet, amount or addresses. |
| `check`, `report`, `verify` | None. They have no network code and each cuts its own network before it reads anything (P2). | Nothing. |
| `web/index.html` | None. Its Content-Security-Policy forbids any request (P10). | Nothing from the page. Loaded from a web server it shows that server your IP address like any page; opened as a file, nothing is sent. |

**Not hidden.** With `--no-tor` the server sees your IP address and that you run zcrowd. By default it does not, but
your network provider sees that you use Tor, the exit relay sees which server you contact and when (up to four exit
relays see one sync, because `sync` keeps four connections), and someone who watches both ends can match timing. Run
`sync` on a schedule, not right before you transact. If Tor fails, `sync` stops and names `--no-tor`; it never goes
direct on its own (T1, T2). The default servers are probably one operator, who sees the block range whatever you do.

**What you type.** An amount or an address that you type is never written to disk, logged, sent anywhere or printed back
as typed (P3). What `check` prints is derived from it: the matches are the entries your amount would be tied to, so the
output is as sensitive as the amount itself; keep it out of scrollback you do not control, CI logs and screen recordings.
A value given as an argument stays in shell history and the process list (the command prints a note saying so), and the
argument parser echoes a rejected argument in its own error; the stdin form (`-`) never does. A transaction id typed for
`verify` is read the same way (`verify -`: no echo on a terminal, else one line of stdin), but `verify` prints the event line with that id, so P3 does not cover it. Its errors never print what was typed (`not a transaction id (64 hexadecimal characters)`, `that transaction is not an event in <data>`); the test is `verify_reads_the_id_from_stdin_notes_one_in_the_arguments_and_advises_spot_checks`.

### N: the note about the network cut

`check`, `report` and `verify` print one `note:` line on stderr that names the layers of the network cut in place (claim P2).
It is printed whenever a layer is missing; with both layers in place only when stderr is a terminal, so `--json 2>&1` stays
plain JSON on a normal Linux machine. Where a layer is missing the note comes first on stderr, so do not merge stderr into
the JSON there. There are seven lines (`<error>` stands for the error text of the operating system; the unit test
`sandbox::tests::the_note_names_the_layers_in_place_and_says_not_cut_without_one` asserts each one):

| Where | Line |
|---|---|
| Linux, both layers | `note: network cut for this command: empty network namespace + seccomp socket filter` |
| Linux, no empty network namespace (user namespaces off or refused) | `note: network cut for this command: seccomp socket filter (no empty network namespace: <error>)` |
| Linux, a CPU the filter is not built for (it exists for x86_64 and little-endian aarch64) | `note: network cut for this command: empty network namespace (no seccomp socket filter: not built for this CPU architecture)` |

## What each check does not cover

- **P1.** In a real sync the server is also asked for the tree states at the heights `start - 1` and `end` of the range and for its server info (which carries the tip's branch id). Those requests carry range heights only, but they are not in the test's list: the test calls `candidates` and `resolve` on the offline fixture source, which serves no tree states. They are read in `ingest.rs` and `source.rs`, not tested. P1 shows the requests of a fake server; what the transport does on the real network is T3's job, and T3 sees addresses and ports, not the content of the requests.
- **P2.** The network cut stops zcrowd's own network use. It is not a barrier between zcrowd and other programs of the same user: the seccomp filter does not block `ptrace`, `process_vm_readv` and `process_vm_writev`, `pidfd_open` and `pidfd_getfd`, or `/proc/<pid>/mem`, and not the `TIOCSTI` ioctl that types into a terminal. A descriptor that `check` inherited from its parent (a socket, say) still works, and files are not restricted (P3 checks only which code writes). None of this was tested. Where the kernel refuses an unprivileged user namespace, only the seccomp filter holds (the note on stderr says so), step (a) is skipped, and the `cargo test` that looks for the namespace is expected to fail there; the seccomp tests do not depend on it. The filter is built for x86_64 and for little-endian aarch64 only. macOS has a no-network profile that was never run; Windows has nothing, and the command prints `network NOT cut`. Mutation runs, by hand once: removing any seccomp rule, dropping thread synchronisation of the filter, installing it only as a fallback, or calling `enter()` without it each made a test fail; removing `sandbox::enter()` from any of the three commands failed the namespace test.
- **P3.** The scan looks for random values, and the sample holds no match for them. A real amount that has a match prints that match's own amount and txid, which is public data and as sensitive as the amount you typed. The scan looks at files in the repository tree and in the fresh HOME, TMPDIR and XDG directories, not at your shell history, scrollback, swap, core dumps or other programs. `verify` prints the transaction id it was given, and P3 does not cover transaction ids. The ignored `data/` and `target/` directories are not scanned (a command that wrote there is caught by the test that no file was created or changed).
- **P4.** A name scan of `crates/`, not of the dependencies; key handling under another name would pass. It shows that the code has no such feature, which is not a proof that it cannot be added.
- **P5.** A scan by crate name, not a review of the 525 crate versions. The Tor client (arti) was not audited by us. The Tor feature took the tree from 248 to 525 crate versions and `Cargo.lock` from 287 to 624 packages. `tracing-subscriber` is among them; the name `tracing` does not occur in `crates/`, so zcrowd installs no subscriber.
- **P6.** The webpki root set is trusted; there is no certificate pinning. Over Tor the same roots are set inside `zcash_client_backend` 0.25.0 (`tor/grpc.rs`; read, not run). The self-signed test runs with `--no-tor` against a local server, because Tor refuses local addresses. A bad certificate over Tor was refused in two hand tests on 2026-10-24, on a build from before the final code, against badssl.com hosts (`certificate not valid for name`, `UnknownIssuer`); that is not an automated test, and it was not repeated on the final code. An expired certificate over Tor is NOT VERIFIED (the test host timed out twice). The branch-id and tree-state checks of P8 trust the same server as the blocks.
- **P7.** Run on the offline fixtures, not on a live sync. The names in `tx/` are checked, not the bytes: they are the raw transactions the server sent, whose ids P8 recomputes.
- **P8.** A server that keeps its story consistent is not detected: compact blocks carry no proof of work, and the tree states come from the same server as the blocks. The block hash chain is checked inside one sync, not between two (the coverage file stores no block hashes). The pool check is weaker when a server serves no tree states: a pool with no data at all in more than 1,000 blocks from NU6.3 on is refused, and a range of 1,000 blocks or fewer from such a server can leave a pool out without being refused (also in the README's NOT VERIFIED list). The source addresses of a shield, which only `--to` uses, come from signature data that the transaction id does not commit to (ZIP 244 puts it in the authorizing digest); a server could swap one and the id check would still pass. The tests use fake servers that lie in the listed ways; the live run shows one real server passing.
- **P9.** One report, generated from the sample.
- **P10.** The script check is a list of API names, not a proof; the CSP is what stops a request. The audit runs Chromium only; Firefox and WebKit are covered by the separate run below, which the audit does not make. Real Safari is NOT VERIFIED. The CSP is a `<meta>` tag inside the file: it protects the copy you opened, and a host that serves you a modified copy is the reason to compare the SHA-256 of `web/index.html` (README section 3). Browser extensions can read what you type.
- **P11.** A pattern scan (home paths, a personal string, mail-like strings), not a review of every file for personal facts.
- **V11.** A Unified Address of a test network is tried; any other kind of address that `--to` does not take (a plain Sapling address, say) gets the same sentence by the code, and no test tries it.
- **N.** Three of the seven lines were seen, the macOS one in CI only (job 121102516531), never on a real Mac. Windows was built and tested in CI only (job 121102516515); no run printed its line (README NOT VERIFIED).
- **R1.** Linux only, and only by hand: `release.yml`, which runs the script for the three targets, has never run on GitHub, so the macOS and Windows archives are NOT VERIFIED. C code that `cc` compiles is not covered by the path remap; the scan would catch a leak from it (this run found none), and the fix would be `-ffile-prefix-map` in `CFLAGS`. The scan looks for the build machine's paths, not for other personal data.
- **T1, T2, T5, T7.** The interposer sees libc calls, not raw system calls. The tests need Linux, `unshare -rn` and a C compiler; without them the audit prints `SKIP`. Tor failing to start is simulated by an empty network namespace (no network at all); a real network that blocks Tor was not tried.
- **T3, T4, T6.** The interposer is evidence, not a packet capture: it sees `getaddrinfo`, `gethostbyname`, `connect`, `sendto`, `sendmsg` and `sendmmsg`, not raw system calls, and DNS on port 53 only when sent through those calls. Zero name lookups of any kind in Tor mode fits the design (the exit relay resolves the server name), but it is not a proof against code that bypasses libc. The Tor leg fetches only 20 transactions, one range, one run. The runs need the network and were made once on `d2f6ea9` (below), not by the offline audit.
- **T8.** The pool tests use fake connections numbered in the order they are made, and the stream tests a fake server: none of them runs real Tor. The two mutation runs were made by hand on earlier builds. That four circuits are faster or steadier was not shown (README, section 4).
- **V.** `cargo test` ran on Rust 1.97.1; under Rust 1.90 only `cargo check` ran (NOT VERIFIED beyond that). One command-line test failed once in a full run on a busy machine because it could not start the binary; it did not return and the cause is unknown.
